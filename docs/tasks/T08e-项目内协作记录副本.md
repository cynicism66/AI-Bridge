# T08e：项目内协作记录副本

## 背景
用户希望"每个项目的合作记录保存在各自的项目里，需要的时候用"。现在所有记录都只在集中数据库 `~/.bridge/bridge.db` 里，项目文件夹里只有手动导出的内容。
用户的决定（DECISIONS 第 39 条）：**集中数据库继续作为主存储，同时自动在每个项目里存一份可读副本。**

## 一、副本的内容和位置
- 位置：`<项目根目录>\.bridge\协作记录-YYYY-MM.md`，按事件发生的月份分文件。
- 内容：这个项目的所有历史事件（消息全文、状态更新、认领、释放、到期、开关、AI 开关、初始化、职务、权限、交接、forget），**格式和 `history` 命令的输出完全一致**，每条一行，按时间顺序追加。消息里的换行保留，续行缩进两个空格，方便阅读。
- 文件开头写一段说明：这是 AI Bridge 自动生成的本地副本，未打码，不要提交到公开仓库；想要打码后的版本请用"导出"。
- **原文不打码**（只存在本地）。

## 二、谁来写，怎么保证不丢不重
- **只由桌面软件写入**，MCP 进程和命令行都不写，避免多个进程同时追加同一个文件。
- 每个项目记下"已经写到哪个事件 id"（存在 `~/.bridge/app.json`，或者数据库里新建一张表，由你决定并在报告里说明）。桌面软件轮询到新事件时，就追加写入；软件没开期间产生的事件，下次启动时从记录的位置接着补齐。
- 写入要保证**不重复、不遗漏**：先追加内容、刷盘，再更新"已写到的 id"。如果写到一半崩溃，下次启动时要能识别出文件末尾最后一条已写入的事件 id（比如每行末尾带上 `<!-- #id -->`，或者用别的可靠办法），避免重复写入。
- 只对**已开启**的项目写副本。项目关闭期间不写；再次开启时补齐关闭前已经产生、但还没写入的事件。
- 项目文件夹不存在或者没有写权限时，跳过这个项目，并在设置页显示原因，不能影响其他项目。

## 三、开关和 .gitignore
- 每个项目有一个"在项目里保存协作记录"的开关（默认开启），放在设置页。初始化向导里也加上这一项（默认勾选），并附带"把 `.bridge/` 加进 .gitignore"（默认勾选）。
- **加入 .gitignore**：只有当项目是 git 仓库、而且 `.gitignore` 里还没有能忽略 `.bridge/` 的规则时，才在文件末尾追加一行 `.bridge/`。使用原子写入，保留原文件的其他内容和换行风格。这是对项目文件的改动，**必须经过用户确认**（向导里的勾选，或者设置页里的按钮）。
- 如果用户没有勾选加入 .gitignore，而项目是 git 仓库，设置页要显示醒目的提醒："协作记录可能会被提交，请注意隐私"。
- 已经初始化过的项目（包括 `D:\Bridge`）：在设置页提供开启按钮和"加入 .gitignore"按钮，**默认不自动开启**，由用户自己决定。

## 四、和其他功能的关系
- **彻底删除**（T08c）：按决策 35，不删除项目文件夹里的文件，所以副本会保留。在删除确认框里补一句："项目文件夹里的 `.bridge\` 协作记录副本不会被删除，如不需要请手动删除"。
- **交接**（T07）：HANDOVER.md 的"项目文档索引"里，如果项目有 `.bridge\` 副本，要把它列出来并说明是本地未打码的记录。
- **导出**：不变，仍然用来生成打码后、可以放进仓库的版本。

## 测试
- Rust：渲染格式和 `history` 一致；追加、补齐、崩溃后不重复（模拟写到一半）；按月分文件；关闭期间不写、重新开启后补齐；.gitignore 追加（已有规则时不重复添加、保留 CRLF、非 git 仓库不创建）；文件夹不可写时跳过。
- 前端：向导和设置页的开关逻辑。
- Windows CI 全绿。

## 审查意见（Claude，代码审查）
**结论：主体通过，但有一个小修复要在部署验收前完成（下面第 1 条）。**

已验证：本机 `clippy -D warnings`、54 项 Rust 测试通过。设计合理：只由桌面程序写入；先追加并刷盘，再保存游标；用每条记录头里的事件 id 和字节长度识别并截掉写了一半的尾部，所以崩溃后不会重复写入；数据库变化时拿历史记录和文件核对；某个项目出错时只影响它自己，其他项目照常写；彻底删除项目时保留 `.bridge` 文件，交接文档索引也已更新。

**关于依赖本机 Git（`git check-ignore`）：同意。** `.gitignore` 的语义很复杂（否定规则、子目录里的 .gitignore、全局的 excludes），交给 Git 判断最准确；AI 编程的用户几乎都装了 Git；Git 不可用时如实提示，不会假装已经受到保护。

**需要修复（部署验收前）：**
1. **没有处理 Git 的"仓库所有者不一致"（dubious ownership）**。复现方法：仓库的 `.git` 目录是由另一个 Windows 账号创建的（比如 AI 工具在沙箱账号下执行了 `git init`），当前用户直接运行 `git check-ignore` 时，Git 会报 "detected dubious ownership" 并以 128 退出；只有加上 `-c safe.directory=…` 才能正常返回。现在的代码会把这个错误原样显示成"Git 无法检查副本忽略规则：fatal: detected dubious ownership…"，用户看不懂。Claude 在本项目的实际环境中确认过这种情况确实会出现。
   - **不要**让 Bridge 自己加上 `safe.directory` 来绕过：这是 Git 的安全机制，应该由用户决定是否信任这个目录。
   - 要做的：识别出这种错误，在设置页显示中文说明："这个仓库的所有者和当前用户不同，Git 出于安全原因拒绝检查。如果你信任这个目录，可以在终端运行：`git config --global --add safe.directory <路径>`，然后点"重新检查""。同时仍然按"无法确认受到保护"处理，显示隐私提醒。
2. **加一层防护**：调用 Git 时加上 `-c core.fsmonitor=false`，防止仓库配置里的 fsmonitor 让 Git 执行别的程序（`--no-index` 已经避开了读取索引，这样可以再多一层保险）。

建议（不阻塞）：设置页里除了"加入 .gitignore"按钮，再加一个"重新检查"按钮，方便用户按照上面的说明处理之后立即刷新状态。
