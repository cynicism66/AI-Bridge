# T08d：等待命令与已读显示（小任务）

## 背景
Bridge 是"AI 主动来查"的模式：用户或另一个 AI 发出的消息，不会自动送到 AI 的对话里。用户觉得"在 Bridge 里发消息得不到回应"很别扭。
Claude 已经用自带的后台监视工具验证过：只要有一个轻量的轮询，一有新消息就把 AI 叫醒，AI 就能自动读取并回复，用户不用切换窗口。
用户的决定（DECISIONS 第 37 条）：**不做界面上的"自动响应"开关**，用户在对话里说一句"开始监视"就行。但要提供一个通用的命令，让 Claude 和 Codex 用同一种方式监视；另外在聊天页显示已读和未读。

## 一、`bridge-mcp wait`
`bridge-mcp wait [项目] --agent <名字> [--timeout <秒>] [--interval <秒>] [--follow]`
- 默认行为：一直等，直到出现一条**发给这个 agent 的新未读消息**（收件人是这个 agent 或 all，发送方不是它自己，而且在命令启动之后才到达，或者 id 大于启动时最大的那条），然后打印一行后退出，退出码 0。
- 打印格式（一行）：`新消息 #<id> <发送方>（<来源>）→ <收件人>：<内容，换行压成空格，最多 200 个字>`。来源标注的规则和公告板一致。
- `--timeout`：超时后退出，退出码 2，打印"等待超时"。默认不超时。
- `--follow`：不退出，每来一条消息就打印一行，一直持续下去（给 Claude 的后台监视工具用）。
- `--interval`：轮询间隔，默认 3 秒，最小 1 秒。**只读**，不改变已读状态，不写数据库，不创建会话。
- 项目未开启、全局关闭或者这个 agent 被关闭时：立即退出，退出码 3，并打印对应的中文原因。这样 AI 就不会在用户关闭协作之后还在监视。
- 项目参数和其他命令一样，可以省略（取当前目录），并按 git 仓库识别。

## 二、已读显示
- bridge-core 的结构化接口里，给每条消息附上"每个收件人是否已读、几点读的"。收件人是 all 时，列出这个项目里所有已知的 AI；human 也算一个收件人。
- 数据库里的 `reads` 表**目前没有记录读取时间**：如果要显示时间，就在数据库版本 7 里加一个 `read_at` 列（旧记录留空，显示为"已读"，不带时间）。如果你评估之后认为不需要显示时间，可以只显示已读或未读，并在报告里说明。
- 聊天页：**你（human）发的每条消息**下面显示一行小字，比如 `claude 已读 16:10 · codex 未读`；AI 发的消息不显示。
- **聊天页每条消息都显示编号**（比如 `#141`），放在发送方旁边；历史页里的消息事件也一样。AI 和用户在公告板上都用 `#编号` 互相引用，用户反馈界面里找不到编号对应的消息。
- 聊天输入框的占位提示改为："AI 不会实时收到消息；它们查看公告板时才会读到。需要马上处理时，请在对应的 app 里提醒它，或者让它开始监视。"

## 三、Codex 能否监视
请你（Codex）调查 Codex app 能不能在后台长期运行 `bridge-mcp wait --follow` 这样的命令，并在收到输出时自动继续工作；或者能不能在一个回合里阻塞运行 `bridge-mcp wait` 直到有消息。**只调查、记录结论，不用做成功能**，写进完成报告。

## 测试
- 契约测试：`wait` 在有新消息时输出正确并退出；超时退出码 2；项目关闭时退出码 3；启动之前就有的消息不触发；自己发的消息不触发；`--follow` 连续输出（测试里用超时结束）。
- 单元测试：已读信息的结构化接口；如果做了版本 7 迁移，也要测迁移。
- 前端：已读那一行的渲染逻辑。
- Windows CI 全绿。

## 验收
部署后：用户在 Bridge 里给 claude 发消息，Claude 用 `bridge-mcp wait --follow` 在后台监视，自动收到并回复；聊天页上用户的消息显示 `claude 已读`。

## 不要做
- 不做界面上的"自动响应"开关，不做自动启动 AI 会话（`claude -p`、`codex exec`），不做 Channels。
