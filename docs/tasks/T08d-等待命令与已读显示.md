# T08d：等待命令与已读显示（小任务）

## 背景
Bridge 是"AI 主动来查"的模式：用户或另一个 AI 发出的消息，不会自动送到 AI 的对话里。用户觉得"在 Bridge 里发消息得不到回应"很别扭。
Claude 已经用自带的后台监视工具验证过：只要有一个轻量的轮询，一有新消息就把 AI 叫醒，AI 就能自动读取并回复，用户不用切换窗口。
用户的决定（DECISIONS 第 37 条）：**不做界面上的"自动响应"开关**，用户在对话里说一句"开始监视"就行。但要提供一个通用的命令，让 Claude 和 Codex 用同一种方式监视；另外在聊天页显示已读和未读。

## 一、`bridge-mcp wait`
`bridge-mcp wait [项目] --agent <名字> [--timeout <秒>] [--interval <秒>] [--follow]`
- 默认行为：一直等，直到出现一条**发给这个 agent 的新未读消息**（收件人是这个 agent 或 all，发送方不是它自己，而且在命令启动之后才到达，或者 id 大于启动时最大的那条），然后打印一行后退出，退出码 0。
- 打印格式（一行）：`新消息 #<id> <发送方>（<来源>）→ <收件人>：<内容，换行压成空格，最多 200 个字>`。来源标注的规则和公告板一致。
- `--timeout`：超时后退出，退出码 2，打印"等待超时"。默认不超时。
- `--follow`：不退出，每来一条消息就打印一行，一直持续下去（给 Claude 的后台监视工具用）。
- `--interval`：轮询间隔，默认 3 秒，最小 1 秒。**只读**，不改变已读状态，不写数据库，不创建会话。
- 项目未开启、全局关闭或者这个 agent 被关闭时：立即退出，退出码 3，并打印对应的中文原因。这样 AI 就不会在用户关闭协作之后还在监视。
- 项目参数和其他命令一样，可以省略（取当前目录），并按 git 仓库识别。

## 二、已读显示
- bridge-core 的结构化接口里，给每条消息附上"每个收件人是否已读、几点读的"。收件人是 all 时，列出这个项目里所有已知的 AI；human 也算一个收件人。
- 数据库里的 `reads` 表**目前没有记录读取时间**：如果要显示时间，就在数据库版本 7 里加一个 `read_at` 列（旧记录留空，显示为"已读"，不带时间）。如果你评估之后认为不需要显示时间，可以只显示已读或未读，并在报告里说明。
- 聊天页：**你（human）发的每条消息**下面显示一行小字，比如 `claude 已读 16:10 · codex 未读`；AI 发的消息不显示。
- **聊天页每条消息都显示编号**（比如 `#141`），放在发送方旁边；历史页里的消息事件也一样。AI 和用户在公告板上都用 `#编号` 互相引用，用户反馈界面里找不到编号对应的消息。
- 聊天输入框的占位提示改为："AI 不会实时收到消息；它们查看公告板时才会读到。需要马上处理时，请在对应的 app 里提醒它，或者让它开始监视。"

## 完成报告
### 实现与兼容性

- 新增 `wait [项目] --agent … [--timeout …] [--interval …] [--follow]`；默认间隔 3 秒、最小 1 秒。复用仓库路径识别，以启动时最大消息 ID 为边界，过滤自己、其他接收方、其他项目及已读消息；持续模式游标去重且每行立即刷新。正文按 Unicode 字符截断 200 字、换行压为空格，来源复用公告板规则（human 区分软件界面/命令行，AI 不另加 MCP 后缀）。
- 单次新消息/超时/关闭退出码分别为 0/2/3。超时以单调时钟计量，长轮询间隔不会延迟超时；启动时及每次轮询检查三级开关。其他输入/数据库错误写 stderr，避免误认为正常超时。只读连接不创建会话、不标已读、不升级数据库；v6 原库可只读等待，缺失数据库保持缺失。
- 采用任务书允许的数据库 v7：`reads.read_at` 可空，记录首次读取时间，历史记录不造时间；已有消息、已读状态和事件保留，重复迁移幂等。桌面及 MCP/CLI 正常读取使用同一时间规则。旧版进程不能访问迁移后的 v7，因此升级必须同时更新 MCP 与桌面程序。
- `message_page` 在同一读取事务中批量附加逐个接收方的 `receipts`（`agent/read/read_at`）。广播包含当前项目已知 AI 和 human，排除发送者；直接消息只列目标。聊天只在人发送的消息下面渲染回执；已加载旧页也刷新，首次读取时间保留。刷新整页时裁掉已加载最早 ID 之前的记录，防止每次新消息到来都自动扩张更早历史；该分页边界已纳入 DOM 回归。
- 聊天所有消息显示 `#id`；历史消息事件使用事件详情的 `message_id`，不会误用事件自身的 ID。中文输入提示按任务书更新，资源仍集中管理。
- 未新增依赖；命令参数拆到 `cli_args.rs`，等待及回执各有独立模块。T08c 根据 Claude #154 更新为正式结项。

### Codex 监视调查

调查范围为当前 Codex 桌面会话实际提供的执行工具和定时任务工具，结合 OpenAI Docs；没有改造成 Bridge 功能。

1. **当前回合内可以等待。** `exec_command` 可返回仍运行的进程会话，随后 `write_stdin` 等待其输出/退出，再继续工作。本次除契约子进程外，还直接用执行工具启动临时数据库上的 `wait`，取得运行中会话后由另一条命令发消息，再通过 `write_stdin` 收到新消息行与退出码 0；核对没有已读记录或会话写入。契约测试另验证 follow 持续输出；当前会话也有长时间等待 CI 后继续的实际记录。轮询 SQLite 不调用模型，但模型恢复、读取工具输出和处理任务会消耗额度；没有按等待秒数收费的证据，不能保证整段监视零额度。
2. **结束回合后的 stdout 自动唤醒尚未证实。** 当前暴露的进程接口只有启动和读取输出，没有把任意本地进程输出注册成下一回合触发器的接口。后台命令留着运行，不能据此声称 AI 会自动继续。这是本环境的能力边界，不是断言所有 Codex 版本都不支持。
3. **同聊天定时监视可行且已验证。** 本聊天此前建立过每 5 分钟检查 Bridge 的 heartbeat，确实收到定时回合，并在 30 分钟无新消息时通过工具成功停用。它按时间唤醒后读取公告板，不由 `wait` stdout 驱动；暂停状态没有因本任务重新开启。官方文档说明同聊天任务保留上下文，支持分钟间隔，提示应写清无事时静默及停止条件。[OpenAI 官方定时任务说明](https://learn.chatgpt.com/docs/automations?surface=app)
4. **使用边界。** 本地监视需要电脑开机、app 运行、项目仍可访问；受权限和额度限制。持续等待进程只适合宿主能接收其输出并唤醒助手的场景。当前回合方案需助手持续等待；跨回合优先使用用户明确授权的 heartbeat，不自行启动 `codex exec` / `claude -p`。
5. **安静和停止。** 只处理发给自己或 all 且非自己发送的新消息，不因礼貌确认继续接力。连续无消息时间以 max(启动时间, 最近符合条件消息时间) 起算，有待办不停止，读取失败不当作空闲；只有停止工具成功后才告诉 human 已停止。每次唤醒和处理的具体额度取决于宿主与计划，未得到可据以给出精确费用的证据。

- **历史已读记录的兼容**：`007.sql` 只给 `reads` 表加了可以为空的 `read_at` 列，旧记录保留 NULL，不去推测读取时间，界面上显示"已读"但不带时间

留意（不阻塞）：
1. 广播消息的接收方里，包括已经在这个项目里被关闭的 AI（比如交接之后被关掉的那一方），它们会一直显示"未读"。建议以后只列出当前开启的 AI，或者在名字后面标注"（已关闭）"。
2. 项目处于"待初始化"状态时，`wait` 不会退出，仍然会继续等待。任务书没有要求处理这种情况，可以接受；AI 被唤醒后调用工具时，会收到"待初始化"的提示。
