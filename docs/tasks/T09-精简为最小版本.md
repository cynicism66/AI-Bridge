## 第 3 步：新增 `bridge-mcp hook`

用法：`bridge-mcp hook --agent <claude|codex>`

Claude Code 和 Codex 的 Stop 钩子格式相同：从 stdin 读一个 JSON，里面有 `cwd`（会话的工作目录）和 `stop_hook_active`（这一轮是不是已经被钩子续过）。

行为：
1. 从 stdin 读 JSON，取 `cwd` 作为项目目录（按 git 仓库识别项目，和 MCP 工具一致）。
2. 以下情况**什么都不输出，退出码 0**（让 AI 正常停下）：
   - `stop_hook_active` 为 `true`（防止无限续跑）
   - 不是 git 仓库、项目未开启、全局总开关关闭
   - 没有发给这个 AI（收件人是它本身或 `all`）的未读消息
   - 读 stdin 或数据库出任何错（钩子出错不能卡住 AI，把错误写到 stderr 即可）
3. 有未读消息时，向 stdout 输出一行 JSON，退出码 0：
   ```json
   {"decision": "block", "reason": "<内容>"}
   ```
   `reason` 用中文，格式：
   ```
   Bridge 公告板上有给你的新消息：
   #225 [codex → claude] 第一部分做完了，请审查……
   #226 [human → all] ……
   需要回复的用 send_message 回复；只是确认收到的消息不用回复。
   ```
   并把这些消息标记为这个 AI 已读（和 `read_messages` 的已读规则一致）。
4. 消息很多时 `reason` 只放最近 10 条，末尾写"还有 N 条，用 read_messages 查看"，并且只把放进去的标为已读。
5. 不写任何配置文件。钩子由用户自己配置（见第 4 步 README）。

### 收件窗口（决策 52）

用户在同一个项目里常会另开窗口只问问题、不改文件。钩子对所有窗口都生效，所以要保证消息只送给"干活的窗口"，不被提问窗口拿走。

每个项目、每个 AI 最多记一个**收件窗口**，用钩子 stdin 里的 `session_id` 标识。需要新增一个迁移建表保存：项目、AI、收件窗口的 `session_id`、它最后一次触发钩子的时间、是否等待重新指定。旧数据不动。

规则（在上面第 2、3 条之前判断）：
1. **还没有收件窗口时**：只有在确实有未读消息要送的时候，才把当前窗口记成收件窗口并送消息；没有消息就不记。
2. **有收件窗口时**：
   - 当前窗口就是收件窗口：更新最后触发时间（`stop_hook_active=true` 时也要更新），然后按上面第 2、3 条处理。
   - 当前窗口不是收件窗口，并且收件窗口最后触发时间在 **2 小时以内**：什么都不做，退出码 0。
   - 当前窗口不是收件窗口，但收件窗口已经超过 2 小时没触发：按"还没有收件窗口"处理，也就是有消息要送时由当前窗口接替。
3. **等待重新指定时**（见下面的 `rebind`）：下一个触发钩子的窗口直接成为收件窗口，**不管有没有消息**，然后按上面第 2、3 条处理。

### 新增 `bridge-mcp rebind`

用法：`bridge-mcp rebind [项目目录] --agent <claude|codex>`，给人用。

- 把这个项目、这个 AI 设成"等待重新指定"。
- 输出中文提示，例如："已清除 claude 的收件窗口。请在要接收消息的那个 claude 窗口里随便说一句话，它这一轮结束后就会成为收件窗口。"
- 项目未开启时照样可以执行（只改这张表）。

测试：用临时数据库（`BRIDGE_DB`）覆盖上面每一种情况，包括：
- `stop_hook_active=true`、没有未读、项目关闭、stdin 不是合法 JSON、超过 10 条
- 第一个有消息可送的窗口成为收件窗口，之后别的窗口触发时什么都不做、消息保持未读
- 收件窗口超过 2 小时没触发，别的窗口接替（测试里用可注入的时间，不要真的等）
- `rebind` 后，下一个触发的窗口在没有消息时也成为收件窗口
- Claude 和 Codex 的收件窗口互不影响；不同项目互不影响
